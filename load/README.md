# Навантажувальний тест: відкриття продажу

`booking-rush.js` моделює старт продажу на популярну подію (зал на 1000 місць):

- **buyers** — 100 покупців без пауз резервують по 2 сусідні місця. Вибір сильно зміщений до перших рядів,
  тож після перших секунд більшість спроб — конфлікти (`409`).
- **browsers** — 100 переглядів карти місць за секунду.

Перші 45 с те саме навантаження йде на окрему подію (прогрів JIT і пулів), у звіт потрапляють наступні 30 с.
Наприкінці скрипт звіряє, що зайнятих місць рівно `2 × створених замовлень`, тобто подвійних продажів немає.

## Запуск

Стек ізольований від основного `docker-compose.yml`: власні Postgres і Redis (дані в tmpfs),
застосунок обмежено 2 CPU, rate limiting вимкнено.

```bash
# з Redis (за замовчуванням)
docker compose -f load/docker-compose.yml up -d --build
LABEL=redis docker compose -f load/docker-compose.yml run --rm k6

# без Redis: резерв місць іде одразу в Postgres, карта місць щоразу з БД
REDIS_CLAIMS=false CACHE_TYPE=none docker compose -f load/docker-compose.yml up -d --force-recreate app
LABEL=no-redis docker compose -f load/docker-compose.yml run --rm k6

docker compose -f load/docker-compose.yml down
```

Параметри через змінні оточення k6: `BUYERS`, `MAP_RATE`, `DURATION_SEC`, `WARMUP_SEC`.
Повний підсумок k6 зберігається в `load/results/<LABEL>.json`.

## Результати

i5-11400H, Docker Desktop (WSL2); застосунок — 2 CPU, Postgres і Redis без обмежень. По два прогони кожного варіанту
на щойно запущеному застосунку.

| | З Redis | Без Redis |
|---|---|---|
| `POST /orders`, запитів/с | **1165 – 1567** | 751 – 779 |
| `POST /orders`, p50 / p95 | **50–70 / 149–186 мс** | 104–109 / 312–331 мс |
| Карта місць (100/с), p50 / p95 | **79–101 / 262–294 мс** | 111–120 / 393–421 мс |
| Продано місць за 30 с | 858 – 868 | 866 – 872 |
| Подвійних продажів | 0 | 0 |

Redis дає в 1.5–2 рази більше обслужених спроб купити за вдвічі меншої затримки: конфліктні спроби відсіюються
Lua-скриптом `SET NX` ще до транзакції, без черги на блокуваннях рядків у Postgres. Коректність від Redis
не залежить — без нього продано стільки ж місць, і так само жодного двічі.

**Чому немає p99.** На Docker Desktop під Windows годинник WSL2-VM кожні кілька секунд коригується назад
(`dmesg`: «Time jumped backwards»). k6 рахує фази запиту за системним годинником, тож ~1% запитів, що були в польоті
в момент корекції, отримують фантомні +39 с. Access log Tomcat (монотонний таймер) підтверджує, що на сервері таких
запитів немає. p50/p95 і пропускна здатність від цього не страждають. На Linux проблеми немає; під Windows можна
запустити нативний `k6.exe` на `BASE_URL=http://localhost:18080`, але тоді вузьким місцем стає проброс портів
Docker Desktop, а не застосунок.
